# 방법론 — 통합 소프트웨어 공급망 보안위협 매트릭스

통합 AI 보안위협 매트릭스 v3.2 · 통합 클라우드 보안위협 매트릭스 v5 · 통합 OT 보안위협 매트릭스와 같은 틀
(분류 → 위험평가 → 실제근거 → 대응 기준 → 관점 문구)을 소프트웨어 공급망에 적용한 방법을 정리합니다.
숫자는 v2 빌드 기준입니다(세부위협 60개, 사고 DB 167건, KEV 판정 80건).

## 1. 설계 원칙

1. **공격면 단계를 도메인으로** — AI 매트릭스처럼 공격 대상(공급망 단계)을 Lv1 도메인으로 쓰고, 클라우드·OT 매트릭스처럼
   ATT&CK 전술을 '공격 단계' 열로 병기합니다. 공급망은 같은 기법(예: 토큰 탈취)이 단계마다 다른 통제로 막히므로
   전술 축보다 단계 축이 통제 지점을 잘 드러냅니다. 'SLSA 위협' 열이 생산(A~G)·소비(H·I) 위치를 함께 보여 줍니다.
2. **산정 로직은 그대로 이식** — 발생가능성 수식(상 = 실제 사고 2건 이상)과 위험도 3×3 표, 근거 수준 4단계, 우선순위 규칙은
   세 매트릭스와 같습니다. 심각도만 공급망 결과 기준으로 새로 정의했습니다(§7).
3. **근거는 공개 출처의 실제 사고 중심** — 사고 DB의 실제 사고만 발생가능성 '상'을 만들고, ATT&CK 절차·KEV·연구 문헌은
   '중'까지만 반영합니다. 범용 기법·범용 취약점이 근거를 부풀리지 않도록 공급망 맥락만 셉니다(§6).
4. **원문 비수록** — 공개 저장소이므로 SLSA·OWASP·S2C2F 등은 ID·명칭만 연계하고, 재배포가 허용된 자료(SAP Risk Explorer,
   CISA KEV)만 원본을 둡니다(`reference/README.md`).
5. **문구는 근거와 기계적으로 대조** — 관점 문구의 사례·수치·ID를 사고 DB·분류 체계와 대조하는 검증기를 빌드 전에 돌립니다(§10).

## 4. 공급망 보안사고 DB (`data/incidents.yaml`)

- **규모**: 167건(2003~2026) — 실제 사고 152건(사고 89 · 캠페인 60 · 정부 경보 3), 연구·시연 15건, 국내 8건,
  2025년 이후 35건(실제 사고 33건).
- **출발점**: CNCF 침해 카탈로그·SAP Risk Explorer '공격' 문헌 88건 → 원 출처로 확인 → 2024~2026년 사고(TeamPCP 연쇄·Shai-Hulud
  계열 웜·axios·Notepad++·DAEMON Tools 등)를 피해 기관 공지·보안업체 분석·정부 경보로 보강.
- **필드**: id · title · date(YYYY-MM) · kind(사고/캠페인/정부 경보/공시/사례연구(익명)/연구·시연/위협인텔) · verification
  (정부·사법 확인 > 피해기관 확인 > 보안업체·연구기관 분석 > 언론 보도 > 행위자 주장 > 논란·원인 번복) · ecosystem(16종) ·
  region · actor · impact(어휘 고정) · summary · sct(매핑 세부위협) · attack_ref(ATT&CK ID) · kev · sources.
- **집계 상태**: 연구·시연 → '실증·연구', 위협인텔 → '위협인텔', 검증 수준이 '행위자 주장·논란·원인 번복'이면 집계 제외,
  나머지는 '실제 사고'(`scripts/taxonomy_rules.py`의 `incident_status`). 연구자의 노출 발견(예: SAS 토큰·Docker 이미지 속 토큰)은
  피해가 확인되지 않으면 실증으로 분리합니다.
- **매핑**: 분석가가 경위를 읽고 단계별로 매핑합니다(계정 탈취 → 악성 게시 → 웜 확산처럼 한 사고가 여러 행에 매핑될 수 있음).
  ATT&CK 캠페인·소프트웨어 ID는 대조·표시용이며 자동 매핑에 쓰지 않습니다.
- **사실 기준**: 요약에는 출처에 있는 사실만 적고, 확인되지 않은 세부(경로·수치)는 쓰지 않거나 완화합니다. 최근 사고는 추가 조사로
  수치·귀속이 바뀔 수 있습니다.

## 7. 평가 로직

- **발생가능성**: 상 = 실제 사고 2건 이상 · 중 = 실제 사고 1건 또는 ATT&CK 사례·KEV·실증·공격 분류 문헌 중 하나 이상 · 하 = 근거 없음.
- **심각도(공급망 결과 기준)**
  - 상: 성공하면 그 자체로 다수 다운스트림에 악성 코드가 정상 신뢰 경로(게시·서명·업데이트·빌드)로 전달되거나, 공급망 인프라
    (소스·빌드·서명·배포·CI/CD·비밀)를 장악하거나, 대규모 금전·파괴 피해가 나는 위협
  - 중: 성공에 사용자의 선택·실수가 필요하거나 피해가 개별 개발자·조직 범위에 머무는 위협, 또는 단독으로는 피해가 없고 다른 위협의
    피해를 키우는 조건·은닉 기법
  - 하: 영향이 제한적·일시적이고 복구가 쉬운 위협 — 해당 행 없음(라이선스·품질 위험은 범위 밖)
- **위험도**: 발생가능성 × 심각도 3×3(상×상 매우 높음, 상×중·중×상 높음, 상×하·중×중·하×상 보통, 나머지 낮음).
- **근거 수준**: 실제 사고 확인 > 실사용 기법 포함(ATT&CK 사례·KEV·위협인텔) > 실증·공개 취약점 > 이론·시나리오.
- **우선순위**: 위험도 → 실제 사고 수 → 최근 사고 수 → SCT-ID.
- **결과(v2)**: 심각도 상 42·중 18 / 위험도 매우 높음 38·높음 16·보통 6 / 근거 수준 실제 사고 확인 58·실사용 기법 포함 2
  (SCT-DP-01.3 AI 패키지 환각 악용, SCT-DP-06 악성 모델 유입).

| 다른 매트릭스 | 실제 사고 | 실사용 | 실증 |
|---|---|---|---|
| AI v3.2 | ATLAS Incident·OWASP 인용 사고 | Realized 기법 | 실증·CVE |
| 클라우드 v5 | 클라우드 사고 DB 실제 사고 | ATT&CK 클라우드 사례 | 연구·노출·벤더 매트릭스 |
| OT | OT 사고 DB | ATT&CK ICS 절차·KEV(OT) | 연구·시연·ICS 권고 CVE |
| 공급망 | 공급망 사고 DB | ATT&CK 공급망 맥락 절차·KEV(공급망) | 연구·시연·SAP 연구 문헌 |

**위험도 포화에 대한 판단** — 60행 중 38행이 '매우 높음'입니다. 공급망 위협은 정상 신뢰 경로로 퍼지는 것이 본질이라 심각도 '상'
기준을 낮추지 않았고, 대신 우선순위(사고 수·최근 사고)로 순서를 매기며 '대응 기준 연계' 시트로 통제 우선순위를 판단하도록 했습니다.
IM(영향·확산) 행은 다른 단계 사고가 모이는 결과 유형이라 상위에 몰리므로, 단계 위협만 볼 때는 IM을 빼고 읽습니다
(IM 제외 상위: PB-01 → PB-02.1 → PB-03.1 → PB-02.2 → SC-03.2 → SC-02.1 → SC-02.2 → SR-02.1 → SC-03.1 → PB-02.3).

## 8. 다른 매트릭스와 비교할 때

- 사고 DB 규모·출처가 매트릭스마다 달라(클라우드 680건·OT 85건·공급망 167건) 위험도·사고 수는 같은 매트릭스 안에서만 비교합니다.
- 같은 위협도 매트릭스별 심각도 기준이 다를 수 있습니다(예: 악성 모델 유입 — 공급망 SCT-DP-06 '중', AI 매트릭스 AI-08-01은 AI 기준).
  연계 ID 열로 오가며 보되 등급은 각 매트릭스 기준으로 읽습니다.

| 필드 | 규칙 |
|---|---|
| `oneline` 핵심 요약 | 50자 이내, '수단 + 대상 + 결과'를 명사형으로(보고서 본문·슬라이드용) |
| `summary` 요약설명 | 2줄 개조식 — ① 공격자는 [수단·경로]로 [행위]할 수 있음 ② 피해·확산 특성 또는 탐지·방어가 어려운 이유 |
| `reference` 참조 | `■ 공급망 관점`(대상·경로·수법·변형·연계 SCT-ID·다른 매트릭스 ID) / `■ 실제 사례`('[라벨] 사례명(YYYY-MM): 경위·결과 (사고 ID·CVE·ATT&CK ID)') |
| `detect` 탐지·대응 | `■ 탐지` / `■ 대응`(예방 → 차단 → 탐지 순, 개발·운영 제약 반영, 매핑된 대응 기준 ID 병기) |

- 라벨: `[실제 사고]` 사고 DB 실제 사고 · `[실증]` 사고 DB 연구·시연 · `[공개 취약점]` CVE·KEV · `[시나리오]` 기준 문서의 가정 사례.
  공개 사례가 없으면 `공개 사고 미확인 — 사유`, 보충 설명은 `참고:`.
- 사례는 그 행에 매핑된 사고만 인용하고, 수치·경위는 사고 DB 요약·출처에 있는 것만 씁니다.
- 용어: 자격증명(인증정보·크리덴셜 쓰지 않음) · 반출(빼내는 행위)/유출(새어 나간 결과) · 게시(publish) · 의존성(dependency).
- v2 결과: 60/60행 작성, 사례 인용 203건([실제 사고] 180 · [실증] 15 · [공개 취약점] 8).

## 10. 검증기 (`scripts/validate.py`, v2)

빌드 스크립트가 워크북을 만들기 전에 자동 실행하고, 오류가 있으면 빌드를 멈춥니다(`--skip-validate`로 생략 가능).

| 대상 | 점검 |
|---|---|
| 원천 데이터 | 사고 ID 형식·중복, 필수 필드, 시점 형식, 사례유형·검증 수준·생태계·영향 어휘, 매핑 세부위협 존재, KEV CVE·ATT&CK ID 존재, 출처 형식 / 분류 체계의 ATT&CK·SLSA·OWASP·CNCF·SAP·S2C2F·SSDF·Scorecard·NIST ID 존재 / KEV 판정 CVE·매핑·구분 |
| 문구 형식 | oneline 50자·중복, summary 2줄, reference·detect 단락 구성과 '- ' 줄, YAML 중복 키 |
| 사례 대조 | 인용 사고가 그 행에 매핑됐는지, 라벨이 집계 상태와 같은지, 사례명 뒤 (YYYY-MM)이 사고 DB 시점과 같은지, CVE가 행의 KEV 판정이나 인용 사고에 있는지, 사례 줄의 ATT&CK ID가 인용 사고 attack_ref에 있는지, 설명 속 수치가 인용 사고 요약에 있는지(경고), 'KEV 등재 N건' 표기가 행의 KEV 판정 수와 같은지(경고) |
| 참조 ID | SCT·ATT&CK·S2C2F·SSDF·OWASP·NIST·Scorecard·다른 매트릭스 ID 존재, 대응 기준·연계 ID가 행 매핑에 있는지, 공급망 관점의 ATT&CK ID가 행 기법·절차 주체인지 |
| 근거 수준 | 실제 사고가 매핑된 행은 [실제 사고] 사례를 하나 이상 인용, 인용 사례가 없으면 '공개 사고 미확인 — 사유' |
| 용어 | 인증정보·인증 정보·크리덴셜·자격 증명 → 자격증명 |
| 시나리오 | 단계별 SCT·사고·ATT&CK ID 존재, 필수 필드, 근거 사고의 매핑 행이 단계에 있는지, 초크 포인트 SCT-ID가 단계에 있는지 |

시험: 시점·라벨·미매핑 사고·행 밖 CVE·근거 없는 수치·금지 용어·없는 ATT&CK ID·연계 안 된 클라우드 ID·50자 초과·YAML 중복 키를
일부러 넣은 사본에서 10종을 모두 잡는 것을 확인했습니다.

## 12. 한계

- **공개 사고 편향**: 보고가 많은 오픈소스(npm·PyPI)·대형 사건 유형이 높게 나오고, 내부 빌드·서명 침해처럼 드러나기 어려운 위협은
  과소평가될 수 있습니다. 국내 사고는 8건으로 공개 자료가 적습니다.
- **근거 중복**: 한 사고가 여러 단계에 매핑되어 행별 사고 수 합이 사고 DB 건수보다 크고, KEV 등재 사례 일부는 사고 DB와 겹칩니다
  (발생가능성 '상'은 실제 사고 수로만 판정).
- **IM 도메인 집계**: 결과 유형이라 사고가 몰려 우선순위 상위를 차지합니다(§7).
- **최근 사고의 불확실성**: 2025~2026년 사고는 1차 공개 자료 기준이며 수치·귀속이 바뀔 수 있습니다(예: GitHub 내부 저장소 수는
  공격자 주장).
- **KEV '악성 코드 내장' 등재**: 악성 버전 패키지가 KEV에 오르는 것은 최근 관행이라 과거 사고는 KEV 근거가 없습니다.

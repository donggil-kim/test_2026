# 통합 보안위협 매트릭스 v3

여섯 원본 매트릭스를 각 원본 데이터 그대로 활용해, 컨설팅 보고서용 **요약 위협 매트릭스 하나**로 통합했습니다.

- **통합 AI 보안위협 매트릭스 v3.2**(LITE, Lv3 124개)
- **통합 클라우드 보안위협 매트릭스 v5**(Lv3 154행, 고유 기법 126개)
- **통합 OT/ICS/IoT 보안위협 매트릭스 v5**(Lv3 141행, 고유 기법·항목 118개)
- **통합 소프트웨어 공급망 보안위협 매트릭스 v2**(세부위협 60개)
- **통합 신원·계정 보안위협 매트릭스 v2**(세부위협 65개)
- **물리·인적 보안위협 매트릭스 v2**(세부위협 45개)

v2(AI·클라우드·OT 163개)에 공급망·신원·물리·인적을 Lv0로 더한 판입니다. v2 산출물은 이력으로 보존합니다.

- **Lv0 구분**: AI / 클라우드 / OT(ICS·IoT 포함) / 공급망(소프트웨어 공급망) / 신원(계정·IdP·비인간 신원·고객 계정) / 물리·인적(물리 침입·감시·포섭·내부자) 보안위협
- **Lv1 도메인**: 원본 분류를 그대로 사용
  - AI: 원본 10개 도메인(D01~D10)
  - 클라우드: 원본 ATT&CK 14개 전술(RD~IM)
  - OT: 원본 ATT&CK for ICS 12개 전술 + 자원 개발, 13개(RD~IM)
  - 공급망: 원본 8개 단계(DE~IM) · 신원: 원본 10개 공격면(AU~IM) · 물리·인적: 원본 7개 공격면(RC~IM)
- **Lv3 세부 위협**: 원본 Lv3의 맥락·내용을 분석해 재구성·재작성 — **합계 258개**
  - AI 124 → 61개, 클라우드 154행(126기법) → 52개, OT 141행(118기법·항목) → 50개
  - 공급망 60 → 33개, 신원 65 → 35개, 물리·인적 45 → 27개
  - 원본 Lv2는 요약표에서 생략하고 원본 상세 시트로 추적
- **Lv3 옆 별도 열**: 핵심 요약 · 위협 설명 · 공격 시나리오 · 대표 사례 · 위험 평가(우선순위 포함) · 대응 방안 · 공격 단계 · 관련 기준 · 연계 위협 · 원본 Lv3 ID
- **보고서 활용**: 본문에는 `보고서용 간략 매트릭스` 시트(핵심 요약·위험도·우선순위·대표 사례 1건·핵심 대응 1줄), 부록에는 `통합 요약 매트릭스`
  - 약 260행이라 보고서 본문은 Lv0별 Top 10과 간략 매트릭스 필터 사용을 권장합니다.

검증 항목:

- **전수 배정**: 원본 AI Lv3 124개·클라우드 고유 기법 126개·OT 고유 기법·항목 118개·공급망 60개·신원 65개·물리·인적 45개가 요약 항목에 빠짐없이, 한 번씩만 배정되었는지
- **문안 형식**
  - 핵심 요약: 한 줄 50자 이내
  - 위협 설명: 2줄, 1줄은 '~위협'으로 종결
  - 시나리오: '→' 흐름 1~2줄 · 사례: 1~2줄 · 대응 방안: 2~3줄
  - 줄당 길이 상한, 금지 용어(인증정보·크리덴셜 등)
- **사례 출처 대조**: 대표 사례의 '사례명(시점)'과 유형 태그가 구성 원본의 참조 열에 실제로 있는지 (새 사실 추가 방지)
  - Lv0별 추가 유형: OT `[위협인텔]`·`[EMB3D]`, 신원 `[위협인텔]`·`[시연]`, 물리 `[정부 경보]`·`[위협인텔]` — 모두 실제 사고로 세지 않음
  - 원본 사례명의 '크리덴셜 스터핑'은 '자격증명 스터핑'으로 바꿔 대조
- **사례 분산(OT·공급망·신원·물리)**: 같은 사고를 여러 항목의 대표 사례로 쓰면 경고
  - 원본 참조 줄의 사고 ID(INC-·SCI-·IDI-·PHI-…) 기준이라, 이름이 다른 같은 사고도 잡음
  - 불가피한 반복은 `common.CASE_REUSE_ALLOWED`에 허용 항목·사유를 등록 (`docs/작성기준.md` 4장 — v3 신규 Lv0는 반복 0)
- **물리·인적 작성 제약**(결정 D9): 대응 방안의 드론 무력화·전파 교란 권고, 모든 열의 보호 특성 표현을 오류로 처리
- **근거 정합성**: 근거 수준이 '실제 사고 확인'인 항목에 [실제 사고] 사례가 있는지, 연계 위협 ID가 존재하는지
  - OT `[EMB3D]` 사례는 구성 원본에 실제 사고·실증 사례가 없을 때만 쓰는지 (v2 결정 D7)

- **원본 재현**: 여섯 원본의 실제 사고 수와 클라우드·OT·공급망·신원·물리 최근 사고 수를 사례 ID·기준일로 다시 세어 원본 값과 일치하는지 확인

## 요약 문안 수정

요약 문안은 `data/` 아래 YAML만 고치고 다시 빌드합니다. 항목 형식:

```yaml
- id: ID-SE-02                      # AI-<도메인번호>-<순번> / CL-·OT-<전술>-<순번> / SC-·ID-·PH-<도메인>-<순번>
  name: 헬프데스크 사칭과 계정 복구 절차 악용   # 세부 위협(Lv3), 30자 이내
  summary: 헬프데스크 사칭·복구 절차 결함으로 비밀번호·MFA 재설정해 계정 인수   # 핵심 요약, 한 줄 50자 이내
  members: [IDT-SE-02.1, IDT-SE-03] # 구성 원본: AI는 UT Lv3 ID, 클라우드는 ATT&CK ID(또는 AZT…), OT는 ATT&CK·EMB3D ID, 공급망·신원·물리는 SCT-·IDT-·PHT- 세부위협 ID
  basis: 본 인증보다 약한 …         # 통합 근거 (단독이면 '단독 유지 — 사유')
  links: [CL-IA-04]                 # 선택: 교차 연계 (양방향으로 자동 표기)
  description: |-
    - … 위협
    - …
  scenario: |-
    - … → … → …
  cases: |-
    - [실제 사고] 사례명(2025-04): 요지
  controls: |-
    - …
    - …
```

위험 평가(발생가능성·심각도·위험도·근거 수준·실제 사고 수·최근 사고·우선순위)는 구성 원본에서 자동 재산정되므로 문안에 적지 않습니다.

- OT 전술 반복 기법은 요약 항목의 주 전술 행 값으로 평가합니다.
- 공급망·신원·물리 문안 골격은 `python3 integrated/scripts/v3_status.py --skeleton <kind> <도메인>`, 대표 사례 후보는 `--cases <kind> <도메인>`으로 봅니다.
- 세부 규칙(OT·공급망·신원·물리 보충 포함)은 [`docs/작성기준.md`](docs/작성기준.md)를 참조하세요.

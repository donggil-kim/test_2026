## 4. 후보 추출과 판정 절차

1. **통합 사고 색인 먼저 구축** — 두 위협이 같은 사고를 공유하는지가 중복 판정의 신호라서 사고사례 목록(6장)을 먼저 만듦
2. **후보 쌍 점수화**(`scripts/dedup_candidates.py`) — v3 258개의 모든 쌍(33,153쌍)에 네 신호를 더해 점수 3 이상 **635쌍**을 추출
   - ① 연계 위협 표기 +2 ② 같은 ATT&CK 기법 +2/기법(상위기법만 일치 +0.5) ③ 같은 실제 사고 +1/사고(최대 5) ④ 명칭·핵심 요약 글자 2-gram 유사도 ×6
   - 사고 공유(③)만 높은 쌍은 대부분 같은 대형 사고의 다른 공격 단계(예: OT 대형 사고 5건, Shai-Hulud)라 중복 아님
3. **클러스터 문안 대조** — 같은 주제의 후보를 약 40개 클러스터로 묶고(노출 시스템 취약점·원격 접속·피싱·사칭·공급망·신뢰 관계·유효 계정·MFA 우회·토큰·위조·저장 비밀·지속성·인증 통제·권한·방어 무력화·C2·CI/CD·데이터 탈취·랜섬웨어·금전·자원 탈취·내부자·위장취업·AI 공급망·에이전트 신원·설비 피해·무선·반입 매체 등) 각 항목의 위협 설명·구성 원본·대응 방안·대표 사례를 직접 비교
4. **판정** — P1~P5로 흡수·그룹·유지를 정하고, 흡수 사유는 각 문안 `absorbs.reason`, 그룹 근거는 `dup_groups.yaml`의 `basis`에 기록
5. **반영** — 흡수 항목 YAML 삭제 → 흡수한 항목에 `absorbs` 추가·문안 보강(19개 항목) → 다른 항목 `links`의 폐기 ID를 흡수 ID로 변환 → 빌드·검증

**흡수 문안 형식**

```yaml
- id: ID-SE-01
  …                                   # 기존 필드 (members는 주관 Lv0 원본만 — 위험 산정 대상)
  absorbs:                            # v4 Lv0 간 통합으로 흡수한 다른 Lv0의 v3 위협
    - id: CL-IA-03                    # 폐기한 v3 위협 ID (재사용 금지)
      name: 피싱 기반 클라우드 계정 탈취   # v3 명칭
      members: [T1566, T1566.002]     # 그 Lv0 원본 키 — 전수 배정·역참조·참고 평가에 쓰고 위험 산정에는 쓰지 않음
      reason: …                       # 흡수 사유 → 부록-Lv0 간 통합 · 재구성 매핑 '통합 근거'
```

- 같은 Lv0 안 통합은 `absorbs`가 아니라 `members`로 합칩니다(검증기가 오류 처리).
- 폐기한 v3 ID는 번호를 당기지 않습니다. 원본 연계 열(신원·물리 원본이 v2·v3 요약 ID를 참조)과 문안 `links`의 폐기 ID는 빌드가 흡수 ID로 바꿉니다.

## 9. 한계·후속 검토

- **Lv0 독자 관점**: 클라우드만 보는 독자에게는 자격증명 접근·초기 침투 일부가 신원으로 옮겨 보입니다. 매트릭스 뷰 이관 표기와
  재구성 매핑(클라우드 원본 행 → 흡수 ID)으로 추적할 수 있고, 클라우드 단독 보고서가 필요하면 클라우드 v5 원본 매트릭스를 쓰는 편이 맞습니다.
- **등급 하향 표시 5건**(5.1): V3 결정의 결과입니다. 보고서에서 위험도를 인용할 때 흡수 원본 참고 등급을 함께 적는 것을 권장합니다.
- **동일 사고 매칭**: 사례명 고유어·시점 기반이라 이름이 완전히 다른 같은 사고(행위자 별칭만 다른 경우 등)는 빠질 수 있습니다. 클라우드 DB는
  사례명이 영문 원문이고 지역·행위자 열이 없어(요약의 '행위자:' 표기만 추출) 해당 열이 비는 행이 있습니다.
- **그룹 판정은 정성 판단**입니다. 다시 볼 때는 `python3 integrated/scripts/dedup_candidates.py --cross`로 점수가 높은데 같은 그룹이 아닌 쌍을 확인하고,
  `dup_groups.yaml`·문안 `absorbs`를 고친 뒤 다시 빌드하면 됩니다.

# 통합 보안위협 매트릭스 — 작성·평가 기준

요약 Lv3 재구성, 위험 재산정, 문안 작성에 적용한 기준입니다. 원본 개별 항목의 산정 규칙은 각 원본 워크북의
평가 기준 시트(AI v3.2 `도메인·평가기준`, 클라우드 v5 `평가 기준`, OT v5 `평가 기준`, 공급망 v2·신원 v2·물리·인적 v2 `평가 기준`)를 따릅니다.
워크북 `부록-작성·평가 기준` 시트(`build_integrated_matrix.CRITERIA`)는 이 문서의 요약본입니다.

## 1. 재구성 원칙

| 구분 | 기준 |
|---|---|

### 1.1 전술 중복 행 처리

ATT&CK에서 여러 전술에 걸친 기법(원본의 중복·반복 행)은 **주 전술 1곳**에만 배치하고,
나머지 전술은 요약표 '공격 단계' 열에 `(연관: …)`으로 표기합니다.

- 전술마다 위험 값이 다른 반복 기법은 요약 항목의 주 전술 행 값으로 평가합니다.
- 예: OT T0851 루트킷은 회피 '중×중', 대응 기능 억제 '중×상' → OT-EV-02는 회피 행 값

### 1.4 공급망·신원·물리·인적 묶음 보충 기준

세 원본은 같은 빌드 틀(자체 분류 체계 → 사고 DB → 관점 문구)로 만들어졌고 Lv1이 자체 도메인이며 Lv2(위협분류)가 이미 있습니다.
재구성안은 [`v3_재구성안.yaml`](v3_재구성안.yaml)에 확정했습니다(공급망 60 → 33 · 신원 65 → 35 · 물리·인적 45 → 27).

| 대상 | 기준 |
|---|---|
| 출발점 | 원본 위협분류(Lv2)를 출발점으로, 같은 Lv2 안에서 통제가 같은 세부위협을 묶음 |
| 단독 유지 | 피해 규모·근거 밀도가 두드러진 세부위협은 단독 유지(예: SC-PB-01 정상 패키지 악성 버전 게시 · ID-AU-03 MFA 미적용 · PH-IN-02 재직자 기밀 유출) |

## 2. 위험 평가 (요약 Lv3 재산정)

요약 항목의 위험 평가는 문안에 적지 않고 **구성 원본에서 자동 재산정**합니다.
AI는 `common.evaluate_ai`, 클라우드·OT·공급망·신원·물리는 공용인 `common.evaluate_attack`을 씁니다
(공급망·신원·물리 원본은 공용 로더 `common.load_taxo`로 읽어 클라우드·OT와 같은 구조로 넘김).

| 항목 | 규칙 |
|---|---|
| 위험도 | **구성 원본별 위험도(발생가능성 × 심각도)의 최댓값**. 발생가능성과 심각도를 서로 다른 원본에서 가져와 조합하지 않습니다(교차 결합 금지). 3×3 표는 아래와 같으며 원본 여섯 매트릭스와 동일 |
| 발생가능성 보정 | 구성 원본의 실제 사고 합집합이 2건 이상이면, 사고가 1건 이상 확인된 원본만 발생가능성을 '상'으로 보정 |
| 발생가능성·심각도 | 위험도 최댓값을 낸 원본(**대표 원본**)의 값을 표시. 동률이면 실제 사고 수 → 심각도 → 발생가능성 순으로 선택. 대표 원본은 `부록-재구성 매핑`의 '위험 대표' 열에 ● 표시. 전술 반복 기법은 요약 항목의 주 전술 행 값 (필요 시 `severity_override`로 근거와 함께 조정 — v1~v3에서는 사용하지 않음) |
| 실제 사고 수 | **AI**: 구성 원본의 ATLAS Incident 유형 사례 ID(중복 제거) + OWASP 인용 사고 수. OWASP 인용 사고는 ID 없이 건수만 있으므로, 원본별 건수 합에서 참조에 같은 사례명(시점)으로 실린 중복분을 뺍니다<br>**클라우드**: 구성 원본의 사고 DB ID(중복 제거) — 집계 대상 유형(사고·캠페인·사례연구(익명)·규제공시(8-K)·위협인텔 보고서, 집계 포함=Y)<br>**OT**: 구성 원본의 OT 사고 DB ID(중복 제거) — '역매핑_사고사례' 시트의 집계가 '실제 사고'인 76건(85건 중). 실증·연구, 위협인텔(배포 전 발견된 공격 도구), 원인 번복 사례는 제외<br>**공급망·신원·물리·인적**: 구성 원본의 사고 DB ID(SCI·IDI·PHI, 중복 제거) — 각 원본 '역매핑_사고사례' 시트의 집계 상태가 '실제 사고'인 사고(공급망 152건/167건 · 신원 116건/126건 · 물리·인적 89건/100건). 실증·연구, 위협인텔, 시연, 물리의 정부 경보·제외(검증)는 세지 않음. 로더가 원본 141·65·45행의 실제 사고 수·최근 사고 수를 사고 ID로 재현해 원본 값과 다르면 빌드를 중단(결정 D11) |
| 최근 사고(2025~) | 실제 사고 중 2025년 이후 사고 수. 클라우드·OT·공급망·신원·물리: 사고 DB 기준일(원본 '최근 사고' 열과 일치 확인). AI: ATLAS 사례 일자 + 참조에 시점이 적힌 OWASP 인용 사고(시점이 없는 인용 사고는 제외) |

**Lv0 간 비교 유의** — 여섯 Lv0는 실제 사고 근거의 밀도와 심각도 기준이 다릅니다.
위험도·사고 수·우선순위는 같은 Lv0 안에서 비교하고, Lv0 간 등급을 직접 비교하지 않습니다.

- 클라우드는 사고 DB(680건) 기반이라 실제 사고 근거가 AI(ATLAS 사례·OWASP 인용)보다 촘촘합니다.
- OT는 OT 사고 DB(85건)와 ATT&CK 공식 절차 매핑이 근거입니다.
- 공급망·신원·물리·인적은 각 사고 DB(167건·126건·100건)가 근거입니다.
- 심각도 기준: OT는 물리적 결과(인명·환경·설비·제어), 공급망은 '상'이 원본 60개 중 42개(포화), 신원·물리는 '상'을 피해 범위가 넓을 때로 제한합니다.

**공급망 위험도 포화** — 공급망 요약 33개 중 28개가 '매우 높음'입니다. 원본 기준(결정 D6)을 그대로 따른 결과이며,
공급망 항목 간 비교는 실제 사고 수·최근 사고·우선순위로 합니다.

**물리 공개 사고 편향** — 물리·인적 원본은 공개 사고 기준이라 기소·판결로 드러나는 기술 유출·내부자 사건이 높게 나오고,
공개·귀속되지 않는 물리 침입·은닉 감시는 과소평가될 수 있습니다(원본 방법론 `physical/docs/METHODOLOGY.md` §12).

**신규 공격면 유의** — 발생가능성은 확인된 실제 사고 기준이라, 공개 취약점은 많으나 사고 보고가 적은 신규 공격면
(예: AI-02-03 간접 프롬프트 인젝션 — 공개 취약점 4건, 확인된 사고 0건 → '높음')은 과소평가될 수 있습니다.

- OT는 공개되는 사고가 적어(과소보고), '이론·시나리오'는 '발생하지 않음'이 아니라 '공개 근거 없음'으로 읽습니다.
- 설계상 인증이 없는 기능의 악용(제어 프로그램 다운로드·운전 파라미터 변조·비인가 명령 메시지)은 CVE가 쌓이지 않습니다.
  공개 취약점 수가 적다고 위험이 낮은 것은 아닙니다.

**OT 근거 편중** — OT 요약 50개 중 49개가 '실제 사고 확인'입니다.

- 원인: ATT&CK 공식 절차가 촘촘한 대형 사고 5건이 원본 36~46행(전술 반복 행 포함)에 매핑돼 있음
  - INC-009 Stuxnet, INC-008 2025 폴란드, INC-004 Triton, INC-003 2016 우크라이나, INC-002 2015 우크라이나
- 실제 사고가 이 5건에서만 확인되는 항목: 6개(OT-RD-02 · EX-02 · EX-03 · PE-01 · PV-01 · LM-01). 개요에 자동 산출해 표기
- 영향 단계 쏠림: IT 랜섬웨어에 따른 예방적 OT 중단이 가장 잦은 실제 영향이라 OT-IM-01에 사고가 몰림(34건)
- OT 항목끼리는 근거 수준 열로 구분되지 않으므로, 실제 사고 수·우선순위로 비교합니다.

## 3. 문안 작성 기준

| 세부 위협(Lv3) | 명사구. 묶은 범위가 드러나게 (예: `인증 통제 변조(MFA·조건부 액세스·장치 등록)`) | 30자 |

- 원본에 없는 새 사실을 추가하지 않습니다. 수치·사례·제품명은 구성 원본의 요약설명·참조(OT는 탐지·대응 포인트 포함)에서만 가져옵니다.
- 용어 통일: **자격증명**(인증정보·크리덴셜 사용 금지 — 검증기가 차단), **반출**(빼내는 행위) / **유출**(새어 나간 결과).
  OT·신원 원문의 '크리덴셜 스터핑'은 '자격증명 스터핑'으로 씁니다(검증기가 원본 쪽을 같은 용어로 바꿔 사례명을 대조).

**OT 보충**

- **핵심 요약**: 대상 계층이 드러나게 씁니다 (예: `인터넷에 노출된 PLC·HMI·웹 제어 화면에 직접 접속해 화면·설정 조작`).
- **대응 방안**: OT 원본 '탐지·대응 포인트'를 요약하되 운영 제약을 반영합니다.
  - 계정 잠금·패치·재부팅이 운전에 주는 영향을 고려합니다(예: '운영 영향을 검토한 로그인 실패 잠금').
  - 보상 통제(망 분리·허용 목록·OT 네트워크 감시·이중화·수동 운전 절차)를 함께 적습니다.
- **용어**: 제어기 · EWS · HMI · 안전계통(SIS) · 현장 장치 · IT/OT 경계 · Purdue 계층으로 통일합니다(7장).

**공급망·신원·물리·인적 보충**

- 원본 '요약설명'·'참조'·'탐지·대응 포인트'를 **요약**합니다. 원본보다 자세한 기법 설명, 단계별 실행 절차·도구 사용법·우회 요령은 쓰지 않습니다.
- **공급망**: 핵심 요약에 공급망 단계(개발·빌드·게시·소비)가 드러나게 쓰고, 대응은 원본 S2C2F·SSDF 통제를 요약합니다.
- **신원**: 신원 유형(인력·특권·NHI·고객)과 ID 환경(온프레미스 AD·클라우드 IdP·SaaS·CIAM)이 드러나게 씁니다.
- **물리·인적 작성 제약**(원본 방법론 §1·§9, 결정 D9 — 빌드 검증기가 금지 표현을 검사)
  - 수법은 탐지·식별에 필요한 '징후' 수준까지만 쓰고, 침입·도청·촬영·포섭의 실행 방법은 쓰지 않습니다.
  - 드론은 탐지·식별·신고·차폐만 권고합니다. 대응 방안에 기체 무력화·전파 교란 같은 표현을 쓰지 않습니다(권한 있는 기관 영역).
  - 인적 징후는 객관적 행동·직무 사실(직무와 무관한 접근, 촬영, 신고하지 않은 금전 제안, 해고·승진 탈락 같은 인사 사건)만 씁니다.
    보호 특성(출신·종교·인종·성별 등)은 어느 열에도 쓰지 않습니다 — 원본 사례 요약에 국적·성별이 있어도 요지에서 뺍니다.
  - 개인은 실명 대신 직책·관계로 적고, 임직원 모니터링은 개인정보보호법·노사 협의 범위로 한정합니다.

| [공개 취약점] | CVE·공개 보안 권고로 확인된 취약점 (OT: CISA ICS 권고·KEV) |
| [실증] | 연구·레드팀·벤더가 실제 제품에서 재현한 공격 (원본 표기 `[실증·연구]` 포함) |
| [ATT&CK 사례] | MITRE ATT&CK에 기록된 그룹·소프트웨어·캠페인의 사용 사례 |
| [시나리오] | OWASP 등 기준 문서의 가상 시나리오 |
| [위협인텔] | **OT·신원·물리**. OT는 배포 전에 발견된 공격 도구의 능력 분석(PIPEDREAM·COSMICENERGY) — 요지에 '배포 전 발견' 성격을 드러냄. 신원·물리는 원본의 위협인텔 보고. 실제 사고로 세지 않음 |
| [EMB3D] | **OT 전용**. MITRE EMB3D 장치 위협(TID) 인용 — 시연·분석 근거. 구성 원본에 실제 사고·실증 사례가 없을 때만 사용 (결정 D7, 빌드 검증) |
| [시연] | **신원 전용**. Browser & Identity Attacks Matrix(SAT) 등 공개 시연 — 실제 사고로 세지 않음 (결정 D8) |
| [정부 경보] | **물리 전용**. 정부·수사기관의 공개 경보(실제 사례 요지 포함) — 원본 규칙대로 실제 사고로 세지 않음 (결정 D8) |
| 공개 사고 미확인 — 사유 | 구성 원본 모두 사례가 없을 때만 사용 (원본 참조에 '공개 사고 미확인'이 있어야 허용. v3 예: ID-PE-03) |

- **출처 대조**: 사례의 `사례명(시점)`과 유형이 구성 원본 참조 열에 그대로 있어야 합니다(검증기 자동 확인).
- **우선순위**: 실제 사고 → 공개 취약점·실증 → ATT&CK 사례·위협인텔 → 시나리오·EMB3D 순입니다.
  근거 수준이 '실제 사고 확인'이면 [실제 사고]를 1건 이상 넣습니다.
- **분산 배치**: 같은 사고가 여러 행에 반복되지 않게 배치합니다. 구성 원본의 유일한 실제 사고라 반복이 불가피한 경우만 허용합니다.
  - 예: APT29 M365 골든 SAML — CL-CA-04·CL-PV-02
  - 예: OpenAI 평가용 자율 에이전트 — 사고의 서로 다른 단계를 AI 4개 항목에서 사용

**OT 사례 분산 (검증기 적용)** — OT는 근거가 대형 5건에 몰려 있어 빌드 검증기가 반복을 검사합니다.

- 사고 단위로 검사: 원본 참조 줄의 사고 ID(INC-…)로 묶어, 이름이 다른 같은 사고(예: '2016 우크라이나'·'2016 우크라이나 송전 변전소')도 반복으로 셈
- 대형 5건은 가장 특징적인 항목에 둠: OT-IR-01 2025 폴란드(와이퍼) · OT-IP-02 2016 우크라이나(명령 전송) · OT-IM-05 Triton(안전계통) ·
  OT-PE-01 Stuxnet(제어 프로그램 변조) · OT-EX-03 2015 우크라이나(HMI 원격 조작)
- 다른 항목은 대형 5건 밖 사고를 먼저 씀
- 불가피한 반복은 `common.CASE_REUSE_ALLOWED`에 허용 항목·사유로 등록했고, 허용 항목 밖에서 다시 쓰면 경고
  - 9건 모두 구성 원본의 실제 사고가 이미 다른 항목에 배치된 사고뿐인 경우임

| 사고 | 허용 항목 | 사유 요지 |
|---|---|---|
| INC-009 Stuxnet | OT-PE-01 · EX-02 · EV-02 | EX-02·EV-02는 실제 사고가 대형 5건뿐 — 주기 실행 블록 감염·PLC 루트킷은 다른 단계 |
| INC-004 Triton | OT-IM-05 · PV-01 · LM-01 | PV-01·LM-01은 실제 사고가 Triton·Stuxnet뿐 — 펌웨어 0-day 권한 상승·SIS 프로그램 추가 |
| INC-008 2025 폴란드 | OT-IR-01 · RD-02 | RD-02는 실제 사고가 Triton·2025 폴란드뿐 — LLM 생성 스크립트·페이로드 재작성 |
| INC-002 2015 우크라이나 | OT-EX-03 · IR-05 | IR-05의 실제 사고 줄이 모두 다른 항목에 배치된 사고 — 변환기 펌웨어 덮어쓰기 |
| INC-003 2016 우크라이나 | OT-IP-02 · EV-01 | EV-01의 대형 5건 밖 사례는 EX-01·PV-02·PE-02에 배치 — 전력 프로토콜 이름 위장 |
| INC-006 2022 우크라이나 | OT-EX-01 · PV-02 | 두 항목 모두 대형 5건 밖 실제 사고가 이 사고뿐 — SCADA 명령 도구 실행·GPO 와이퍼 배포 |
| INC-007 리비우 지역난방 | OT-IP-01 · PE-03 | PE-03의 대형 5건 밖 사례는 2022 우크라이나·리비우뿐 — 웹셸 지속성 |
| INC-013 Dragonfly | OT-IA-06 · EX-04 | EX-04의 대형 5건 밖 사례는 Dragonfly·2022 우크라이나뿐 — 메일 첨부 설치 파일 실행 |
| INC-018 VPNFilter | OT-DS-02 · CO-03 | 두 항목 모두 대형 5건 밖 실제 사고가 이 사고뿐 — 패킷 스니퍼·ssler 중간자 모듈 |

**공급망·신원·물리 사례 분산 (검증기 적용)** — 사고 DB 기반이라 같은 사고가 여러 세부위협에 매핑돼 있어 OT와 같은 방식으로 검사합니다.

- 사고 단위(SCI·IDI·PHI)로 검사하며, v3에서는 세 Lv0 모두 반복 0건이라 `CASE_REUSE_ALLOWED`에 등록한 항목이 없습니다.
- 신원은 재구성안(`v3_재구성안.yaml`)에 대표 사례 후보를 Lv0 안에서 겹치지 않게 미리 배치했고 그대로 썼습니다.
- 물리·인적은 `v3_status.py --cases`로 구성 원본의 사례 줄을 보고 **국내·최근 사고를 우선**해 골랐습니다(결정 D7).
  27개 항목의 대표 사례 54건 중 국내 사고 21건 · 2025년 이후 사고 8건입니다.
- 다른 Lv0와 같은 사고를 쓰는 것은 허용하되, 같은 사고면 서로 다른 단계를 씁니다
  (예: 북한 원격 IT 인력 단속 — ID-LC-03은 위장 취업의 계정 획득, PH-IN-01은 랩톱 팜 수색).

## 5. 교차 매핑·추적 열

| 열 | 산정 |
|---|---|
| 공격 단계 | **AI**: 구성 원본 '주 공격 단계'(ATLAS 전술) 합집합을 클라우드(ATT&CK v19.2 국문) 용어로 통일 — 초기 접근→초기 침투, 내부 확산→횡적 이동, 유출→반출 (방어 회피처럼 1:1 대응 용어가 없는 단계는 원문 유지)<br>**클라우드·OT**: 주 전술 + `(연관: 원본 중복·반복·이동 전 전술)`<br>**공급망·신원·물리**: 구성 원본 '공격 단계' 합집합(원본 용어 — 물리는 접근·내부자화 등 물리·인적 단계 포함)<br>단계 구분은 쉼표(명령·제어처럼 이름에 가운뎃점이 있어서). 원본 상세 시트는 원문 그대로 |

연계 위협의 출처:

- **원본 연계 열**
  - 클라우드 'AI 매트릭스 연계(UT)'(7개 기법)
  - OT '클라우드 매트릭스 연계'·'AI 매트릭스 연계(UT)'(7개 기법)
  - 공급망·신원·물리 '다른 매트릭스 연계' 열 — 요약 ID(AI-·CL-·OT-)는 그대로, 상세 ID(OTC-·SCT-·IDT-·PHT-)는 그 원본이 배정된 요약 ID로 자동 변환
    - 추적성을 위해 전부 싣기로 확정(작업 방향 5.3) — 일부 신원·공급망 항목은 연계가 9~10개. 보고서에서 줄이려면 빌드에 표시 상한을 둠
- **문안 `links`**: 요약 작성 때 검토한 연계
- **OT 원본 연계 중 요약 ID로 바로 바꿀 수 없는 참조**: 문안 `links`로 지정 — 대체 여부를 빌드가 확인하고, 없으면 경고
  - 클라우드 v5에 없는 T1584 → OT-RD-01이 CL-RD-01과 연계
  - AI Lv2 ID UT-03 → OT-RD-02가 AI-01-05와 연계
- **공통 Enterprise 기법 기준 OT 연계**: 항목당 1~2개만 채택(예: OT-IM-02↔CL-IM-01 T1486, OT-LM-04↔CL-CA-01·CA-05 T1110·T1552·T1555)

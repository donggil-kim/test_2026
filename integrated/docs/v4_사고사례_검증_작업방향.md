### 2.3 이미 한 검증과 하지 않은 검증

| 구분 | 내용 |
|---|---|
| 이미 한 것 (내부 정합성) | 원본 DB 검증기 — ID 형식·중복, 필수 필드, 시점 형식, 출처 형식, KEV CVE·ATT&CK ID 존재, 대표 사례의 '사례명(시점)'이 구성 원본 참조에 있는지. 통합 빌드 — 사례 ID 유일, 참조 위협 ID 유효, 실제 사고 수 재현 |
| 하지 않은 것 (외부 사실 검증) | 사고가 실제로 있었는지, 날짜·수치·행위자가 공개 자료와 맞는지, 출처 URL이 살아 있고 그 주장을 뒷받침하는지, 동일 사고 묶음이 정말 같은 사고인지 |

기존 검증은 '목록이 원본 DB와 같은가'이고, 이번 작업은 '원본 DB가 현실과 맞는가'입니다. 원본 DB 오류는 목록과 대표 사례 문안으로 그대로 전해지므로(P-11)
검증은 목록 단위로 하고, 정정은 원본 사례 ID를 따라 원본 DB에서 합니다.

## 5. 검증 항목과 판정 기준

### 5.1 검증 축

| 축 | 질문 | 판정 값 |
|---|---|---|
| A 존재 | 그 사고가 공개 자료로 확인되는가 | 확인 · 부분 확인 · 미확인 · 해당 없음 |
| B 시점 | 목록의 시점이 발생월과 최초 공개월 중 어느 쪽과 맞는가 (두 날짜를 모두 기록) | 발생월 일치 · 공개월 일치 · 둘 다 일치 · 둘 다 아님 · 불명 |
| C 핵심 내용 | 요약의 날짜·수치·조직·행위자·CVE·피해 유형이 맞는가 | 일치 · 부분 일치(수치·귀속 차이) · 불일치 |
| D 사례 구분 | 실제 사고 · 실증·연구 · 공개 취약점 · ATT&CK 사례 · 위협인텔 분류가 맞는가 | 적정 · 재분류 제안 |
| E 출처 | 출처가 정확한가 (5.3) | 정합 · 보강 필요 · 오류 · 직접 열람 불가 |
| F 묶음 | 한 행에 묶인 원본 기록이 같은 사고인가 (77행) | 정당 · 분리 필요 · 해당 없음 |
| G 대표 사례 문안 | 그 사례를 인용한 대표 사례 줄의 사례명·시점·요지가 확정된 사실과 맞는가 (P-11) | 일치 · 수정 필요 · 해당 없음 |

C축은 행 전체의 '그럴듯함'이 아니라 **주장(claim) 단위**로 판정합니다. 먼저 요약에서 날짜·수치·기관·행위자·CVE를 뽑아 항목별로 대조합니다
(요약·사례명에 CVE ID가 있는 행 63 · 요약에 수치 표현이 있는 행 260 — 정규식 추정).
G축은 웹 검색을 새로 하지 않고, C축에서 확인한 사실과 대표 사례 줄을 대조합니다(대표 사례 인용 행 368행에 걸린 요약 매트릭스 사례 줄).

### 5.2 허용 오차

| 대상 | 기준 |
|---|---|
| 시점 | 월 단위 값은 월이 같으면 일치, 일 단위 값은 ±3일. **발생월·공개월 어느 쪽과도 다르면 '둘 다 아님'(수정 필요)**. 한쪽만 맞는 행은 F2 확정 뒤 기준에 따라 일괄 판정 |
| 수치 | 출처가 제시한 값(범위)에 들면 일치. 출처끼리 다르면 '출처 차이'로 두 값을 병기 (예: ChainDrop 패키지 수 400+ · 444 · 868 · 1,300+) |
| 행위자 | 공식 귀속 · 벤더 귀속 · 자칭(주장)을 구분해 기록. 주장만 있는 귀속은 목록에도 '주장'이 드러나야 일치 |
| 사례명 | 영문 원제와 국문 표기가 같은 사건을 가리키면 일치 |

### 5.3 출처 정확성 3단계

| 단계 | 내용 | 현재 환경에서 |
|---|---|---|
| ① 표기 정합 | 매체·연도·제목·URL 형식이 맞고 연도가 사고 시점과 모순되지 않는가 | 가능 |
| ② 존재 | 그 URL·제목이 실제로 있는가 | 간접 확인(검색 결과에 같은 URL·제목) |
| ③ 지지 | 출처가 해당 주장(날짜·수치 등)을 실제로 뒷받침하는가 | **F3 상향 시에만 가능** |

집계기관명 단독 행은 ① 집계기관 등재 확인(ramimac 자동 대조 · Wiz 검색) → ② 독립 1·2차 출처를 찾아 주장 대조 → ③ 출처 열에 넣을 URL 제안(F6) 순으로 처리합니다.

### 5.4 증거 규칙

- 판정마다 근거 URL 1개 이상(2025~2026 사건은 독립 출처 2개 또는 1차 출처 1개), 검색일, 짧은 발췌·요지를 원장에 남깁니다.
- 출처 신뢰 등급: **1차** 피해 조직 공지 · 정부·사법 문서 · SEC 공시 · 벤더 원 보고서 · 공식 CVE/KEV / **2차** 주요 언론·보안 전문 매체 / **3차** 블로그·요약 사이트·위키·집계. 3차 단독은 '부분 확인'이 상한입니다.
- 검색어는 요약 문장을 그대로 붙이지 않고 사건명·조직·행위자 같은 고유어로 만듭니다(목록 서술을 되돌려받는 순환을 피함).
- **미확인**은 서로 다른 검색어 3회 이상과 집계기관 등재 확인 뒤에만 붙이고, '허위 확정'과 구분합니다(없음의 증명은 불가).

### 5.5 종합 판정 (행 단위)

| 판정 | 조건 |
|---|---|
| 통과 | A 확인 · B 발생월 또는 공개월 일치 · C 일치 · E 정합(또는 직접 열람 불가로 간접 확인) · G 일치 |
| 경미 수정 | 존재는 확인, 시점 기준 상이(F2 확정 후) · 수치 출처 차이 · 출처 보강 필요 |
| 수정 필요 | B 둘 다 아님, 행위자·피해 규모·기간 등 핵심 사실 오류, 사례 구분 오류, 출처가 주장과 무관·부재, G 수정 필요 |
| 확인 불가 | 독립 출처를 찾지 못함(5.4 조건 충족 후) |
| 구조적 검증 불가 | 익명 사례연구(65행)·ATT&CK 그룹 같은 비사건 행 — **보고서 실재와 해당 사례 서술 여부**, ID·이름 일치로 대체 |

### 6.3 P2 표본과 확대 규칙

- 층 = 대표 DB × 연대(~2019 · 2020~2022 · 2023~2024), 층당 30%·최소 5행(층 규모 이하) → **138행 / 383행**.
- 표본 오류가 0건이면 P2 전체 오류율 상한은 약 2%입니다(95% 신뢰, 3/n 근사).
- **확대 규칙**: 층에서 '수정 필요'와 '확인 불가'가 5% 이상이면 그 층을 전수로 넓힙니다. 전체를 넓히면 최대 245행(검색 약 400~500회)이 더 듭니다.

**선별 기준** — 실제 사고 확인(필수) · 매트릭스 위협 매핑 가능(필수, 아니면 신규 위협 후보) · 중요도: 피해 규모(유출 건수·금액·운영 중단) · 파급(당국 조치·공시·다수 기관) · 새 수법(AI 에이전트·음성복제·딥페이크 등) · 국내 관련성 · 최근성.
시도에 그친 캠페인·전망 기사·단일 출처 보도는 '관찰'로 둡니다.

## 11. 한계와 위험

- 웹서치 결과는 합성 요약문 + 링크입니다. 요약문에도 출처 간 수치 차이나 "2차 보도뿐"이라는 단서가 섞여 나오므로, 판정은 링크로 확인한 근거로만 합니다.
- 2025~2026년 사건은 2차 보도 의존도가 높고 초기 수치가 자주 바뀝니다. 수치 판정에 '기준일'을 함께 적습니다.
- 웹서치는 미국 대상 검색이라 국내 보도가 덜 잡힐 수 있습니다(URL 행 중 국내 도메인 31행: 물리·인적 21 · 신원 9 · 공급망 1). 파일럿에서는 한국어 질의가 동작했습니다.
- 시점 기준(F2)에 따라 B축 결론이 크게 달라집니다. 기준을 정하기 전 결과는 발생월·공개월을 함께 남겨 두어 나중에 한 번에 판정합니다.
- 익명 사례연구(65행)와 요약 없는 행(2행)은 사건 단위 확인이 불가능합니다. 보고서 단위 확인으로 대체하며 통과율 통계에서 따로 셉니다.
- 같은 모델이 검색하고 판정하므로 검색어 편향이 남습니다. 교차 검수(Phase 4)에서 다른 검색어로 재판정해 줄입니다.
- W2의 'AI 활용'은 언론이 제기한 추정이 많습니다. 확인·추정을 구분해 표시하고, 위험 산정에는 실제 사고 여부만 반영합니다(AI 활용 여부는 산정에 쓰지 않음).
- W2 '빠진 사고' 판정은 키워드 대조라 표기가 다른 같은 사고를 놓칠 수 있습니다. ② 중복 확인에서 사건 요지로 다시 대조합니다.
- 정정은 원본 매트릭스 6종 중 고친 것의 소판 갱신을 부릅니다. 원본 매트릭스를 따로 배포한 적이 있다면 그 판과 달라지는 점을 결과 요약에 적습니다.
- **범위 밖**: 사고와 위협 ID의 매핑 적정성(참조 열), 목록에 없는 원본 DB 사고(클라우드 DB 680건 중 목록 미수록분 등). 필요하면 별도 작업으로 다룹니다.
